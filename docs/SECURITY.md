# Security notes

This document describes what the current code actually does, what it does not do, and how to operate it safely. It is not a certification or a penetration-test report.

## Authentication

| Control | Status |
| --- | --- |
| Password hashing | `scrypt` with a random 16-byte salt, N=16384, r=8, p=1, 64-byte key. |
| Plaintext password storage | Never stored in `db.json`; not returned by any API. |
| Bootstrap admin | Provisioned from `.env` only when no administrator exists. Password policy: ≥10 chars, at least one letter and one number. |
| Login rate limit | 12 attempts per 15 minutes per IP, in memory. |
| Reset request limit | 5 per hour per IP. |
| Reset completion limit | 10 per hour per IP. |
| Password-change limit | 8 per 15 minutes per IP. |
| Result search limit | 20 per minute per IP. |
| Contact limit | 5 per hour per IP. |
| Reset tokens | 32 random bytes, stored as SHA-256 hashes, single use, 60-minute expiry. |
| Session cookie | `kadc_session`, `HttpOnly`, `SameSite=Lax`, `Path=/`, optional `Secure`, 12-hour sliding expiry. |
| Session revocation | Password change revokes other sessions; user deactivation/password reset by an admin revokes all sessions. |
| Role source | Server-side user record on every request; the client cannot assign its own role. |
| Self-promotion | No self-registration; user-management endpoints require the admin role; admin cannot change their own role or deactivate themselves. |
| Last admin protection | Server refuses to remove/deactivate the last active administrator. Supabase migration adds the same rule in a trigger. |
| Public result access | Requires examination + roll + registration; only published results/exams; generic not-found response. |
| Fake authentication | None. Failed login returns 401 and issues no session cookie. |

## Request and browser hardening

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`
- Production CSP: `default-src 'self'`, scripts from self, styles from self + Google Fonts, fonts from self + Google Fonts + data, images from self/data, connections to self, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`.
- HSTS in production when the request is HTTPS.
- `Cache-Control: no-store` on auth, dashboard, admin and personal result-search responses.
- State-changing requests with an `Origin` header are checked against `APP_ORIGIN` and the request host. Non-browser clients without `Origin` are allowed, which is standard for this pattern; `SameSite=Lax` cookies provide the browser-side CSRF layer.
- React escapes rendered content by default; the app does not use `dangerouslySetInnerHTML`.
- Uploads: one file per request, 8 MB limit, MIME allow-list, random stored filename, no directory traversal (`path.basename` check), downloads sent with `Content-Disposition` through controlled routes.
- Zod schemas validate request bodies; generic CRUD uses per-entity schemas and partial updates.
- Admin entity deletion is blocked for important records (`USE_ARCHIVE`); referenced records cannot be deleted.

## Data protection

- `server/data/` and `.test-data/` are gitignored. `.env` is gitignored.
- The local data store is plain JSON on disk. Disk encryption, file permissions and host security are the operator's responsibility.
- Automatic JSON backups are **not encrypted**. Store off-server copies in an encrypted location and restrict access.
- Audit logs retain actor id/name/role, action, entity, entity id and details. They are capped at 2,000 entries in local mode.
- Contact messages may contain personal data. Only administrators can read them; deletion creates a backup first in local mode.
- Student dashboards expose only the signed-in student's own data. Teacher dashboards expose only students in assigned sessions.

## Known security limitations

1. **Local JSON store, single process.** No row-level concurrency control. Multiple instances would overwrite each other. Use the PostgreSQL path before scaling.
2. **In-memory rate limiting.** It resets on restart and is per instance. Add edge/WAF limits for a public deployment.
3. **No MFA, SSO or CAPTCHA.**
4. **No e-mail delivery.** Password reset links are logged to the server console in development and can be generated by an administrator. Anyone with console/log access can read them.
5. **No malware scanning** for uploaded documents. Treat uploads as untrusted and scan them out-of-band if the public can influence them (currently only admins upload).
6. **No automated dependency/security scanning** in this repository.
7. **No formal CSRF tokens.** The app relies on `SameSite=Lax`, origin checks and JSON content types. Consider a double-submit CSRF token if the deployment cannot guarantee same-site cookies.
8. **CSP allows inline styles** (`style-src 'unsafe-inline'`) because of the styling approach. Scripts are not allowed inline.
9. **Local backups are plaintext and limited to 25.** They are not a replacement for database PITR.
10. **Supabase RLS is a design, not yet exercised.** No live database was available in this environment. Run the RLS checklist with real anon/student/teacher/admin JWTs before launch.

## Privacy and content rules

- Do not publish student lists, guardian phone numbers, dates of birth, addresses, marks or results beyond an individual's own published result.
- Do not upload documents containing personal data unless the college has a lawful basis and an access policy.
- Do not publish unverified claims about affiliation, recognition, pass rates, fees or deadlines. Use the verification-pending wording.
- Contact form submissions should be retained only as long as needed to respond.

## Incident checklist

1. Deactivate the affected account and revoke sessions (user management → status `inactive`, or password reset).
2. Rotate the bootstrap/admin credentials and any hosting secrets.
3. Preserve logs: audit log export, server logs, reverse-proxy logs, data-directory backup.
4. If data was exposed, identify the data categories and notify the college authority according to its policy and applicable law.
5. Patch the cause, then re-run `npm run typecheck`, `npm run test:api` and the manual auth/privacy checks in [`TESTING.md`](TESTING.md).
6. Record the incident and the remediation.

## Reporting a problem

Report security issues privately to the college's designated website administrator. Do not post personal data, credentials or exploitable details in a public issue.
